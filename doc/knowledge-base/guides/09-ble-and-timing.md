# BLE、封包完整性與時間

BLE 的連線、有效資料與可用回饋是不同狀態。連線成功不代表封包內容完整；接收到角度也不代表裝置故障已解除；控制指令送出不代表硬體已執行。驗證應以資料與事件鏈定義成功。

ATT 的 notification 包含操作碼與屬性 handle，傳統單一通知承載上限為協商 `ATT_MTU−3`。若實際資料長度為 L，必須滿足 MTU 與程序要求，或設計可驗證的分段重組。韌體呼叫設定 MTU 是本地上限請求，不代表與每個主機都協商成功。新版 Core 文件亦不代表 IRMS 芯片支持全部功能。[ATT](../sources/DOC-BLE-ATT.md)、[GATT](../sources/DOC-BLE-GATT.md)

Notification 沒有 ATT 層對每筆通知的確認，與 Indication 的語意不同。不能據此認定完全沒有下層傳輸機制，也不能把 notification 當成應用層已持久化的確認。需要可靠的命令／更新程序時，應明確定義狀態、確認、超時、取消及重試。

| 測試維度 | IRMS 實例 |
|---|---|
| 格式 | 空欄、缺欄、重複欄、非有限值與截斷 |
| 向量延伸 | `V:` 必須有六個有效值，不能只接受半側 |
| 版本 | 舊角度封包與向量／校準路徑分別標記 |
| 連線 | 主動斷線、意外斷線、重連、錯誤狀態 |
| 時間 | 正常間隔、批次延遲、停頓與主機排程 |
| 回饋／OTA | 各階段確認、裝置拒絕、超時及中止 |

裝置採樣時刻、傳輸時刻、主機接收時刻及資料提交時刻不應混成同一時間。主機 epoch 時間適合記錄日期；訊號積分及延遲應使用單調時鐘。沒有裝置時間戳與序號時，主機只能量到到達間隔，無法把每個缺口唯一歸因為未採樣、丟包或主機延遲。[時間格式](../sources/DOC-RFC3339.md)、[ESP Timer](../sources/DOC-ESP-TIMER.md)

建議原始資料品質報告包含接收間隔分布、最大停頓、截斷／錯誤計數、斷線與恢復時間；若未來擴協定，可考慮裝置序號與採樣時間。這是研究與工程需求，不是本次更改協定。
