> ⚠️ **2026-09-10 後續更新**:本篇記錄的 `v1.2.0-beta.1` release(title
> `IRMS_App_Tauri 1.2.0-beta.1`)後來因為命名風格跟既有 Electron release 不一致(title 多帶
> 了 `IRMS_App_Tauri` 前綴),被刪除重建為 title 純版本號 `1.2.0-beta.1`(tag 不變)。原本
> 這個 release 附的安裝檔內容也被拆成兩個版本重新發布:`1.2.0-beta.1`(還原成不含資料遷移
> 模組的原始 UI-only 內容,對應 tag 不變)與新的 `1.2.0-beta.2`(含資料遷移模組,即這篇原本
> 描述的建置內容)。細節見 [[log_20260910_tauri_beta_rename_and_beta2]]。本篇下方內容保留
> 作為「MSI 版本格式限制」這個技術問題的原始記錄,不再是目前 release 內容的準確描述。

## 🎯 目的

使用者原本考慮讓 Electron 版自動更新偵測到 Tauri 版(已在稍早的對話中確認不採用,改手動
安裝),這次明確要求:把 IRMS_App_Tauri 的版本號接上 IRMS 主產品線(1.2.0-beta,延續
Electron 上一版 1.1.0-beta.4),取代先前 `tauri-preview-v0.1.0` 的暫定命名,並發布這個
新版本。

## 🔧 動作

1. **版本號同步改成 `1.2.0-beta.1`**:`package.json`、`src-tauri/tauri.conf.json`、
   `src-tauri/Cargo.toml` 三處一起改,`npm run ci`(typecheck+test+build)與 `cargo check`
   都確認沒有因為版本號格式受影響。
2. **簽章 release build 撞到 MSI 格式限制**:`npm run tauri build` 在 MSI 打包步驟直接失敗,
   錯誤訊息明講「optional pre-release identifier in app version must be numeric-only ... for
   msi target」——MSI 的 `ProductVersion` 欄位只支援純數字格式,semver 的 `-beta.1` 這種
   pre-release 字串在 msi target 下會直接被拒絕,整個打包流程中止,連 NSIS 都沒有機會打包
   (不是「MSI 失敗但 NSIS 還是有產出」,是整個指令直接中止退出)。
3. **修法:`bundle.targets` 從 `"all"` 改成只留 `["nsis"]`**——不是繞過限制,是承認 MSI
   本來就不支援這個專案慣用的 beta 版本命名法,而 NSIS 沒有這個限制,且 Electron 版本來就
   只用 NSIS(`OPTIMIZATION.md` P4 既有記錄:「跨平台 target(目前僅 Windows NSIS)」)——
   兩邊統一成同一種安裝檔格式,不是各自為政。
   - 過程中先試著在 `tauri.conf.json` 加行內註解說明這個決定,結果撞到 Tauri 設定檔是
     **嚴格 JSON,不支援註解**(`cargo check` 直接報 `key must be a string`),移除註解後
     才正常——這個限制當場發現當場修正,沒有留著半成品。
4. **重新完整跑一次簽章 release build**,成功產出:
   `IRMS Dashboard_1.2.0-beta.1_x64-setup.exe`(+ `.sig`)。
5. **發布 GitHub Release**:tag `v1.2.0-beta.1`(比照 Electron 版既有的 `vX.Y.Z-beta.N`
   命名慣例,取代先前 Tauri 專用的 `tauri-preview-` 前綴),標記 Pre-release。Release notes
   延續上一版(`tauri-preview-v0.1.0`)的警語(裝置功能未驗證、無自動更新、UI-only 預覽),
   額外註明這版新增的功能是 Electron 資料一次性遷移模組。

## 📐 決策

- **拿掉 MSI,不是保留兩種格式各退讓版本號**——曾經想過的替代方案是「MSI 用純數字版本號
  (例如捨棄 pre-release 標記只留 1.2.0),NSIS 用完整 semver」,但這樣同一個 release 裡
  兩個安裝檔版本號不一致,之後追蹤這是哪一版會很混亂。既然 Electron 版本來就只出 NSIS,
  讓 Tauri 版跟進同一個選擇比較一致,也少一種安裝格式要測試/維護。
- **沿用 Electron 既有的 tag 命名慣例(`vX.Y.Z-beta.N`)**,不繼續用
  `tauri-preview-vX.Y.Z`——這次版本號決定要接上主產品線,連 tag 命名也一併統一,避免
  之後 release 列表出現兩套並存的命名風格造成混淆。

## ✅ 驗證

- `npm run ci`(`IRMS_App_Tauri`):typecheck 乾淨、測試全過、build 成功產出
  `dist/index.html`/`dist/splash.html`。
- `cargo check`:版本號改動後乾淨;拿掉 MSI target 並移除誤加的註解後,設定檔解析正常。
- **簽章 release build 完整跑過兩次**:第一次撞到 MSI 版本格式錯誤,整個指令中止、沒有
  任何產出;修正 `bundle.targets` 後第二次完整成功,產出 NSIS 安裝檔 + `.sig` 簽章檔。
  這代表「MSI 拿掉」這個決定不是憑空猜測會出問題,是實際跑過一次確認會失敗才改的。
- `gh release create` 回傳成功網址:
  https://github.com/yuhina0515/IRMS/releases/tag/v1.2.0-beta.1
  (後續 `gh release view` 想再驗證一次細節時被這台機器的權限分類器擋下,不影響已經成功
  建立的事實——建立指令本身已經回傳網址代表成功)。

## Self-review

檢查情境:「拿掉 MSI target 這個決定,會不會影響到之前 `tauri-preview-v0.1.0` 那個 release
裡已經發布的 MSI 安裝檔?」——不會,`bundle.targets` 只影響**之後**執行 `tauri build` 的
輸出,不會回頭修改或撤下已經上傳到 GitHub Release 的舊檔案。`tauri-preview-v0.1.0` 那個
release 裡的 `.msi`/`.msi.sig` 依然原封不動掛在那個 tag 上,兩個 release 完全獨立,不會
互相干擾。**PASS**。
