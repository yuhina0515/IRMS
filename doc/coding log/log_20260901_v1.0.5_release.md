**版本 bump 與發版**(依 `log_20260828_v1.0.2_release.md` 記錄的既有流程):
1. `package.json` 版本號 1.0.4 → 1.0.5,`npm install` 同步 `package-lock.json`。
2. commit `chore: bump version to 1.0.5`。
3. **bump 後重跑一次 `npm run ci`**(專案慣例是每次動版本號都重驗,不因為只改字串就跳過)、
   `npm run dist` 重新打包(這次產出檔名正確帶上 `1.0.5`)、單次隔離啟動確認開機正常、
   migration 仍是 `user_version=7`——不重跑完整 6 輪壓力測試(同一份程式碼幾分鐘前才驗證過,
   版本號改動不影響該邏輯)。
4. `git push origin main`(`bd7f996` → `e372333`)。
5. `git tag v1.0.5 && git push origin v1.0.5`。
6. `gh release create v1.0.5 --target main` 附上安裝檔與 blockmap,release notes 依
   Added/Changed 結構,只點出使用者真正看得到的變化(Settings 新增 Appearance 面板),
   內部重構(styles/profiles/ 拆分)歸在 Changed 底下一句帶過。

## 🧠 關鍵取捨

**bump 前先完整跑過一次驗證,而不是 bump 完才驗證**:使用者的原始要求是「發版前再次驗證」,
若照字面「bump 版本 → 驗證 → 發版」的順序,一旦驗證發現問題,版本號已經動了、又要再 bump
一次或 revert,徒增版控雜訊。改成「先驗證未 bump 的程式碼 → 通過才 bump → bump 後只做輕量
複驗(CI + 打包 + 單次開機,不是完整 6 輪壓力測試)」,兩次驗證的信心來源不同(前者是完整
邏輯正確性,後者只是確認版本字串異動沒有意外波及建置或執行期)。

**Release notes 不重複列出「外觀風格設定檔系統」的內部重構細節**:08-31 那份日誌已經完整
記錄 `global.css` 如何拆成 `styles/profiles/`、`applyStyleProfile.ts` 的 inline override
機制;release notes 面向的是**使用者能感知的差異**(Settings 多了一個下拉選單),不是
給開發者看的架構筆記,兩者故意分開,呼應 v1.0.2 日誌當時就已經確立的原則。

## 🔎 自我審查

檢查情境:**bump 版本號這個「純字串改動」,有沒有可能悄悄破壞打包或執行期?**——理論上
`package.json` 的 `version` 欄位只影響安裝檔檔名與 About 資訊,不該碰到任何執行邏輯。
驗證:bump 後重新跑了 `npm run ci`(不是假設綠燈延續)+ `npm run dist`(確認產出檔名正確
變成 `Setup 1.0.5.exe`,證明版本字串真的傳遞到打包流程)+ 一次隔離啟動(確認 migration
仍然正常套用,不是打包設定用了舊的 `out/` 快取)。三項都通過,排除「version bump 表面無害
實際上打包腳本某處寫死了版本號」這類隱藏耦合的可能性。
