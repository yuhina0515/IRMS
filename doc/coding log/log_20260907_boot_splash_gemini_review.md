# 2026-09-07 變更日誌 — 開機動畫依 Gemini 覆核重做

> **相關文件**:[[HOME|導覽首頁]] · [[log_20260907_boot_splash_and_code_splitting|原始實作日誌]] ·
> `doc/gemini-handoff-20260907/01-boot-splash.md`

## 🎯 目的

把當天稍早完成的開機動畫(見上一篇日誌)截圖與真正的 Logo PNG 一起送給 Gemini 覆核。
回覆的核心批評:原本手繪的 SVG 線稿「太過單薄且破碎」,銳角折線拼湊感重,完全沒有
原圖作為醫療儀器的沈穩感;並針對幾何、色彩、時序、繞圈設計、Stage2 轉場給了具體
規格。依標準的 Gemini UI 設計委任慣例直接實作,沒有回頭跟使用者確認美術判斷本身。

## 🔧 動作

- **幾何重構**:4 條指節折線改成 3 條角度精確分佈的斜線;原本拆成 palm/rstem/rleg
  三段的折線,合併成一條連續路徑(`M12,102 C32,150 68,175 100,175 C116,175 126,166
  116,150 L146,110`)——從左下延伸、平滑彎曲,再折返形成 R 型右腿,不再是三段各自
  獨立的折線拼接。
- **訊號節點**:移除原本「外環+內填色」的複雜圓點設計,改成純實心圓;為了在透明
  視窗(背景是使用者桌面,不是白底)上模擬「鏤空」錯覺,沒有用 Gemini 建議的深色
  實色描邊(那樣在淺色桌布上會變成一圈突兀的黑框),改用低透明度的深色描邊
  (`stroke: rgba(0,10,20,0.35)`)——技術上等價,但適應了 Gemini 沒設想到的
  「疊在任意桌布上」這個真實限制。
- **配色與線寬**:結構色(指節+主幹)改為 `#0056B3`(原 `#1d6fd6`);訊號/高光色
  改為 `#00E5FF`(原 `#22d3ee`),搭配 `drop-shadow(0 0 6px rgba(0,229,255,0.6))`。
  結構線寬 12、訊號弧線寬 7(約 60% 比例)。結構線本身**不再加發光**——只有訊號弧
  與圓點保留 glow,呼應「結構=扎實、訊號=高光」的區分,而非全部線條都发光的
  「電影開場」感。
- **時序收緊**:總組裝時間從 1.4 秒縮到 1.1 秒(`SPLASH_ASSEMBLY_DONE_MS`),各元素
  delay/duration 依 Gemini 給的表格重排(指節 0/30/60ms、主幹 150ms、弧線
  400/480ms、圓點 640–780ms)。地板時間常數 `SPLASH_ASSEMBLY_FLOOR_MS` 隨之等比例
  調整(維持「比組裝完成晚 650ms」的既有防呆邏輯,見上一篇日誌的 self-review)。
- **繞圈重做**:兩個圓弧改成不對稱設計——內圈 120° 掃角、1.4s 週期;外圈 80° 掃角、
  2.1s 週期,兩者都順時針、都繞同一個中心(`transform-box:view-box` +
  `transform-origin:95px 105px`),外加一個共用的 `opacity 0.7↔1.0` 呼吸動畫
  (2s 週期),避免長時間卡在載入畫面時顯得死板。
- **Stage2 轉場**:`#orbit` 進入 stage2 時不是單純淡出,而是疊加一個
  `scale(1)→scale(1.8)` + `opacity→0` 的「能量釋放」動畫(300ms),且刻意保留原本
  的旋轉動畫繼續播放(不 remove `.spin`)——讓爆散效果帶著旋轉的「動能」,而不是
  瞬間定格再消失。邊框(`#frame`)的淡入也從單純的 `transition:opacity` 改成
  `@keyframes frame-glow-in`:一開始沒有光暈,35% 時發光強度衝到尖峰(`0 0
  15px`),100% 時平滑降回原本的常駐發光(`0 0 18px`)——時間長度抓
  `SPLASH_GROWTH_DURATION_MS`(550ms)一致,讓「光暈尖峰→回穩」剛好跟「視窗放大
  →抵達最終尺寸」同步完成。連帶把 `SPLASH_ADVANCE_LEAD_MS` 從 250ms 降成
  0——原本這個常數是留給「先讓交叉淡出/淡入穩定一下再開始放大視窗」的緩衝,但
  現在邊框動畫本身就是照著放大時長設計的,兩者必須同時觸發,不能再有額外延遲。

## 📐 決策

- 圓點「鏤空錯覺」沒有照搬 Gemini 建議的深色實色描邊,改用半透明深色——這是本篇
  日誌唯一一處沒有逐字照做的地方,原因記在上面的「動作」段落:Gemini 的覆核是看著
  截圖給意見,截圖背景剛好是白色(Playwright 截圖预设),但 splash 視窗實際是
  `transparent:true` 疊在使用者桌面上,不會永遠是白底。半透明版本在白底跟深色
  桌布上都不會出現不自然的黑框,同時仍然達成「與底下藍色路徑之間有一圈邊界」的
  視覺目的。
- 沒有重新設計主結構的 glow——Gemini 的規格只明確提到訊號色要有
  `drop-shadow`,沒有要求把它也套用在結構線上;結合「視覺重量必須扎實」的整體
  批評方向,拿掉結構線的發光(讓它單純是一條扎實的深藍線,不带模糊光暈)比照抄
  一份訊號色的發光濾鏡更符合這次覆核的精神。

## ✅ 驗證

- `npm run typecheck` / `npm run test`(286 tests)/ `npm run build` 全綠。
- 用 `_electron.launch()` 對打包後的 App 做端到端截圖驗證:組裝中、組裝完成
  (含圓點)、繞圈中(不對稱雙弧清晰可見)、Stage2 爆散+邊框光暈尖峰四個階段都
  截圖確認實際渲染符合預期,不是只看程式碼推論。

## Self-review

檢查情境:「`#orbit.bursting` 疊加 `scale(1.8)` 動畫時,如果同時 `#mark-wrap` 的
`.fading` 也在把整個容器(含 orbit)的 opacity 往下拉,兩個 opacity 效果會不會互相
打架,讓爆散動畫還沒播完就已經被外層歸零、視覺上看不到完整的放大過程?」——把
`#mark-wrap` 的淡出時間從 220ms 調整成跟爆散動畫一致的 300ms(而非保留舊的
220ms 讓外層更快歸零蓋掉內層動畫),並用上面「驗證」段落的 `v2_4_burst`
截圖直接確認:截圖當下爆散中的線稿仍然可見(半透明放大狀態),不是提前消失——PASS。
