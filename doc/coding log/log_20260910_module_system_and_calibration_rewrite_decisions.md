## 🎯 目的

延續 09-09/09-10 對話中浮現、尚未拍板的兩個構想(App 端執行期動態模組系統、校正體驗改為
環境式/自動偵測),逐項提出決策問題請使用者拍板,並在決策的同時直接把結論寫回
`OPTIMIZATION.md`/`TAURI_MIGRATION_PLAN.md`,避免構想只停留在對話紀錄裡。過程中使用者
帶出一個新的、更急迫的實測回報,改變了原本的討論方向。

## 🔧 決策過程與結果

### 1. 校正體驗改為「環境式/自動偵測」構想 — 否決

使用者否決文件裡原本浮現的收斂方向(背景比對幾何預期值,一致就不跳精靈畫面),原話訴求
是「希望裝置可以像手機一樣不需要校正，讓我們在開發時就直接調整好」——這正是 09-09 對話
一開始就已經被釐清方向錯誤的同一個起點:校正量的是**這次穿戴**時感測器實際貼裝角度與
病患腿型的站直基準,每次穿戴都不同,沒有「開發時調一次永久對」的裝置端固定值可寫死。
若要真正免校正,技術上只剩**機構方式**(固定卡榫/導引槽強制貼裝角度)一條路,這是硬體
變動,不是 App 端議題。當場向使用者說明這個限制,請其重新考慮。

### 2. 校正架構本身「認不出哪個環節錯」— 定位到與 09-08 會議相同根因

使用者改口:目前校正功能一團亂,試了每個方向都無法辨識是哪一個環節出錯,想藉模組化機會
把校正邏輯整套推掉重練。追蹤現有架構(`calibration.ts`)確認:這正是
[[log_20260908_meeting_single_imu_axis_orientation|09-08 會議]]已經診斷過的根因——兩顆
感測器綁死一起、走同一套線性六步精靈,無法單獨重測一顆有問題的感測器,驗證信號本身也是
綁在一起判定,所以「認不出哪個錯」。09-08 會議裁決的修法(`recalibrateAxis(limb)` 獨立
單肢段判定)正是針對這個問題設計,但尚未寫進 code。

### 3. 排序決策:先修 09-08 裁決,還是等模組系統就緒整套重練?

提出三個選項(A 先實作 09-08 裁決當獨立修補;B 跳過 A、等模組系統就緒後整套重練;
C 先修 09-08 裁決,之後模組系統就緒再把修好的邏輯包成模組)。**使用者選 B**:不單獨搶修,
校正邏輯重練整個排入模組系統的第一個模組,等 Phase 4 到位、裁決會議開完才動工。09-08 的
核心數學(原始向量旋轉 + `atan2`)保留為重練時的參考起點,不是被推翻,只是實作時機延後。

### 4. 「往不同方向重練」的意思

確認是**開發階段並行嘗試多種校正演算法/流程,最後只保留驗證後最準的一套發布**,不是要做
成讓使用者自選校正方式的產品功能——避免誤解成要在 UI 上暴露多套校正邏輯選項。

### 5. 模組系統本身的三個懸而未決子決策

- **模組來源**:第一方 vs 開放第三方 plugin marketplace——使用者尚未想清楚,**暫定
  第一方**當規劃假設,不是拍板決定,留給裁決會議重新確認。
- **是否需要動工前裁決會議**:**是**,比照 09-07 Tauri 遷移先例,Phase 4 到位後不直接
  進入設計/實作,先開一次三方裁決會議。
- **動態載入完整性驗證**:**定案採用** SHA-256 checksum + 簽章驗證(比對釋出時內建公鑰),
  金鑰管理/驗證失敗行為等細節留到那次裁決會議展開。

### 6. 寫回文件

- `OPTIMIZATION.md`:「App 端執行期動態模組系統」條目更新為已確認方向(含上述三個子決策
  與校正模組重練決定);「校正體驗改為環境式/自動偵測」條目標記為已否決並關閉,說明
  收斂到校正模組重練決定,不再獨立追蹤。
- `TAURI_MIGRATION_PLAN.md`:「Future consideration」段落補上 2026-09-10 的三項子決策,
  並記錄校正邏輯重練是這個模組系統的第一個目標模組,連結回 09-08 會議的參考設計。

## 📐 決策

- **不單獨搶修 09-08 裁決的校正 bug**——使用者的判斷是與其修一次舊架構、之後模組化時
  又要再重做一次,不如直接把「認不出哪個錯」這個急迫問題留到重練時一次解決,用模組系統
  的重新設計順便解掉,不做兩次工。這是使用者明確的排序取捨,已記錄動機供之後回顧。
- **09-08 的診斷與核心數學不作廢**——它仍是校正邏輯重練時最省力的起點(已經過交叉詰問、
  已排除兩個不可行的替代方案),重練不代表從零開始重新分析問題,只是實作/整合的時機挪到
  模組系統就緒之後。
- **模組來源(第一方/第三方)刻意不在這輪拍板**——使用者明講「還沒想清楚」,寫死成
  假設而非決定,避免之後裁決會議被文件裡「已拍板」的措辭誤導,略過該討論的問題。

## ✅ 驗證

- 純文件/決策紀錄工作,無程式碼變更,不適用 `npm run ci`。
- 交叉核對 `IRMS_App_Tauri/src/services/calibration.ts` 現有實作,確認 09-08 會議診斷的
  「二元 axisSwap 判定抓不到部分耦合」與使用者今天描述的「認不出哪個錯」症狀,兩者根因
  一致(`detectAxisSwap` 的 `swap: dRoll > dPitch` 二元判定、`buildCalibrationPatch` 把
  兩顆感測器的驗證與寫入綁在同一次呼叫裡)——不是憑印象假設兩者相關,而是實際讀了現行
  程式碼路徑後確認。
