# 2026-08-31 會議紀錄 — 「A面校正功能」可行性評估

> **相關文件**:[[HOME|導覽首頁]] · [[log_20260829_meeting_auto_calibration_feasibility|2026-08-29 校準精靈自動化會議(高度相關,結論不同但脈絡相通)]] ·
> [[log_20260831_style_profile_system|同日:外觀風格設定檔系統]]

## 問題

使用者手寫筆記提出:「因裝置不在手上,為解決此問題,新增校正A面校正功能(將整個裝置放在平面,
並且透過左右移動校正方向,為了避免重置誤差,僅設定方向)」——即新增一個校準步驟,把感測器裝置
**離體平放**於桌面等平面,透過左右移動來校正方向(離散的 axisSwap/invert 類旗標),刻意只設定
方向、不動連續量的 zeroRaw/offset。

使用者本人已確認此提案與兩天前(2026-08-29)被否決的「用固定安裝幾何+佩戴側純推算取代即時擷取」
提案是**不同的東西**——這次仍然是真的移動裝置、擷取真實感測器數值,只是動作換成離體平放滑動而非
現行六步真人穿戴流程。使用者要求先開會評估,再決定是否實作、範圍多大。

## 與會者與立場(Round 1,三方獨立、互不可見)

- **A(務實派/建造優先)**:主張現在就做,定位為第 5 步(外展,對平衡受限患者最難的一步)以外
  的補充流程,理由是 `detectAxisSwap`/`buildCalibrationPatch` 是純函式,對「裝置在哪裡」沒有任何
  假設,理論上可套用於離體擷取的資料。
- **B(量測物理風險分析)**:直接讀 `IRMS_Sensor/imu.h` 韌體原始碼反駁——`accPitch`/`accRoll` 是
  `atan2f(ay,az)`/`atan2f(ax,az)` 算出的**重力參考傾角**,量的是姿態(相對重力的旋轉),不是位置。
  筆記字面描述的「平放後左右滑動」是**平移**,裝置相對重力的姿態不變,`dPitch`/`dRoll` 近乎零,
  連現行 `CAPTURE_DELTA_MIN`(20°)/`CAPTURE_ROLL_DELTA_MIN`(15°)的有效性門檻都過不了——字面上的
  這個動作量不到任何東西,不是「量得不準」,是「根本沒有信號」。
- **C(病患/照護者操作與產品安全)**:獨立提出同一個物理論點,並額外指出:即使改成能產生真實
  delta 的動作,roll-invert(外展方向)依 README §2.1 定義是「相對穿戴者身體中線」的方向,離體裝置
  沒有中線、沒有肢段側別可言,這是**指涉對象不存在的範疇錯誤**,不是幅度問題,任何離體動作都補不上。
  並指出若真的實作,會把 `thighRollVerified`/`shinRollVerified` 標成「已驗證」卻其實驗證不了任何
  東西——比 2026-08-28 的「沿用舊值但誠實不宣稱信心」缺陷更糟,是斷言一個不可能為真的信心。

## 交叉詰問(Round 2)

把 B(`atan2f` 重力參考傾角、平移不產生 delta)與 C(「外側」需要中線這個離體裝置沒有的參照物)的
論點原文轉給 A 反駁。**A 讀了 `imu.h` 原始碼自行驗證後完全讓步**,明確區分存活與死亡的部分:

- **死亡**:「現在就做,當補充流程」——筆記字面描述的滑動動作連自家的擷取有效性門檻都過不了。
- **死亡**:「離體/裝置在哪裡都一樣」的「substrate-agnostic」論述——A 承認自己把「不管裝置放在
  什麼表面上」跟「不管動作是平移還是旋轉」混為一談,這是真實的推理錯誤。
- **死亡,且無法靠改動作挽救**:任何「取代第 5 步」的主張——即使把動作從滑動改成傾斜/翻轉,能
  產生真實訊號,那也只是一個帶符號的數字,要把它稱為「外側」需要一個不存在的身體參照,這個問題
  出在指涉對象、不是訊號幅度,沒有任何離體動作能補上。
- **窄幅存活**:一個經過修正的「傾斜/翻轉」(而非滑動)動作,理論上可以產生足夠的 delta 去檢驗
  「哪個實體旋轉軸對應哪個回報通道」——但這頂多是韌體軸線接線的開發者除錯用途,不是面向病患的
  校準輸入,且需要預先知道裝置外殼與晶片軸的固定對應關係(製造常數,非執行期未知量)。

## 裁決

**否決此提案(依筆記字面描述),不進 backlog、不排入 ROADMAP/OPTIMIZATION。**

理由(依論點品質而非語氣自信度排序):

1. **字面描述的動作在這套硬體的感測原理下是物理上惰性的**——`accPitch`/`accRoll` 是重力參考傾角
   (`atan2f`),平放後左右滑動是平移,不改變裝置相對重力的姿態,量不到任何東西,連現行有效性門檻
   都過不了。這不是「精度較低的替代方案」,是「這個描述的動作根本沒有做到它宣稱要做的事」。
2. **即使修正動作,也無法替代第 5 步外展**——「外側」的定義需要穿戴者的身體中線這個參照物,離體
   裝置沒有這個參照物,是範疇錯誤而非幅度問題。
3. **若真的實作,會製造比既有缺陷更嚴重的失效模式**——把無法驗證的訊號標成「已驗證」
   (`*RollVerified = true`),比 2026-08-28 的「沿用舊值但誠實」更危險,因為它斷言了一個不可能
   為真的信心,在臨床相鄰的產品裡這是不能接受的失效模式。
4. **與兩天前的否決同一個根本教訓**——這個 codebase 15 天內兩次因為信任「未經即時人在場驗證的
   固定假設」而出過生產環境缺陷(2026-08-14 offset 加倍、2026-08-28 wearSide/roll 沿用舊值),
   本提案雖然形式不同(真的有擷取動作,不是純幾何推算),但字面上量到的訊號量根本不存在,結論
   同樣是:不能繞過真人在場、即時量測這個唯一有實績的機制。

**存留的窄範圍可能性**:一個內部/開發者用的韌體軸線接線診斷(離體傾斜/翻轉裝置,確認哪個實體軸
對應哪個回報通道),明確排除任何病患/照護者使用場景,且絕不寫入 `Settings`/`CALIBRATION_TRANSFORM_KEYS`
任何欄位。本次會議建議**不需要另外實作**——2026-08-22 已加入的 Serial 遙測(見
[[log_20260822_firmware_mtu_diagnostics_and_serial_telemetry|日誌]])已可覆蓋這類開發期軸線確認需求,
新增專門 UI 屬於不必要的範圍擴張。

## 最強的存留疑慮(需要監控)

A 讓步後仍指出一個一般性但真實的觀察:任何校準程序(包含現行六步精靈)的可信度都取決於操作者
是否正確理解要求的動作——這不是本次提案獨有的弱點,但提醒了「離體診斷」即使未來真的要做,操作者
沒有身體關節的自然限制去糾正錯誤動作,比在體上動作更容易被錯誤心智模型帶偏。若日後真的要做前述
窄範圍的韌體診斷工具,應在文案上明確要求操作者對照裝置外殼上的固定標記,而非憑感覺猜測旋轉軸。
