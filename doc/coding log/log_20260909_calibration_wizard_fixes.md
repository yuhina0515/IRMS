# 2026-09-09 變更日誌 — 校準精靈實測回報修復 + 側邊欄收合持久化

> **相關文件**:[[HOME|導覽首頁]] ·
> [[log_20260828_calibration_wearside_and_preview_stutter|08-28 配戴側與確認頁卡頓修復]]

## 🎯 目的

使用者在學校用真實裝置實測 1.1.0-beta.3,回報三個問題:
1. 站立校正(步驟 2/6)無論如何都無法進到下一步——後續查出是忘記帶 `config.h`/`imu.h`
   一起燒錄,韌體編譯失敗,不是這次的範圍(見同日對話紀錄,韌體重燒後校正本身能跑)。
2. 步驟 5/6(腿向外側擺,選配)校正後不知道為什麼會一直跳回前面步驟。
3. 免手擷取有時不會自動開始,而且秒數感覺太少;另外 App 啟動後側邊欄選單會自動展開。

## 🔧 動作

### 1. 動作幅度驗證改為即時檢查(`components/CalibrationWizard.tsx`)

**根因**:前抬大腿/後勾小腿的動作幅度(≥ 20°)驗證原本只在最終 `finish()`(步驟 6)透過
`buildCalibrationPatch` 做——使用者在步驟 2/3 就已經做完真正決定成敗的那個動作,卻要再走
過 2、3 個步驟才在步驟 5/6 被送回步驟 2 或 3 重捕,體感上完全對不起來是哪裡出的錯,只覺得
「怎麼一直跳回前面」。

**修法**:新增 `DELTA_CHECK` 對照表,`handleCapture()` 在自己的擷取完成當下就用
`detectAxisSwap(baseline.mean, stats.mean, limb).delta` 立即驗證,不足 20° 就地顯示錯誤、
停在原步驟,不推進 `step`。`finish()` 裡 `buildCalibrationPatch` 的同一組檢查保留作為防線
(理論上此後不會再被觸發,但留著不放大范围——它是通用純函式,不該假設呼叫端一定先驗證過)。

### 2. 免手擷取的觸發軸向修正(`services/calibration.ts` + `CalibrationWizard.tsx`)

**根因(這是這批修復裡最確定的一個真實邏輯 bug)**:免手擷取判斷「有沒有動」原本用共用的
`PITCH_AXES = ['thigh', 'shin']`(前抬大腿、後勾小腿兩步共用),完全不含 roll 軸。但這支
精靈存在的目的正是偵測感測器貼歪 90°——貼歪時,真正的彎曲動作會落在 roll 軸而非 pitch
軸,`PITCH_AXES` 完全看不到這個位移,免手擷取的動作幅度門檻永遠達不到,使用者只能改用
手動按鈕。換句話說:**免手擷取原本對它最該幫助的那群使用者(感測器貼歪的人)完全失效**。

**修法**:新增 `THIGH_AXES = ['thigh','thighRoll']`、`SHIN_AXES = ['shin','shinRoll']`,
分別對應大腿/小腿步驟,與最終驗證 `detectAxisSwap`(本肢段自己的 pitch/roll 取最大)用
同一組判準,觸發門檻與驗收標準終於一致。

### 3. 免手擷取的樣本數門檻放寬(`CalibrationWizard.tsx`)

`AUTO_MIN_SAMPLES` 從 20 降到 15。原本以 25Hz 理想封包率的保守值抓 20 筆(1.5 秒理想上
約有 37 筆),但實測環境(連線品質、距離、干擾)的實際封包率常明顯低於理想值,20 筆在
較差連線下可能整個 1.5 秒窗口都湊不滿,免手擷取因此「有時完全不會自動開始」——不是判定
邏輯錯誤,是門檻對實際封包率太樂觀。`AUTO_STABLE_MS`(1.5 秒的時間長度)本身不動,只降低
窗口內需要湊滿的筆數。

### 4. 倒數秒數與說明文字對齊(`CalibrationWizard.tsx`)

發現一個原本就存在、直接可見的落差:每一步的說明文字都寫「保持姿勢約 4 秒」,但擷取按鈕
上寫的是「倒數 3 秒」——`COUNTDOWN_SECONDS` 從 3 改成 4,兩處終於一致。使用者原話「秒數
也太少了」很可能就是注意到這個落差。

### 5. 免手擷取新增「偵測中」提示(`CalibrationWizard.tsx`)

擺好姿勢後到真正觸發倒數之前,原本完全沒有任何畫面回饋,容易被誤讀成「沒反應」。新增
`autoWatching` 判斷(免手開啟 + 未在擷取 + 已連線 + 在步驟 1–4 之間),把提示文字換成
「偵測中,請擺好姿勢並保持穩定…」。沒有做即時進度百分比(0~1.5 秒細部進度)——只換一句
靜態文字,成本與風險都最低,先用最小改動看使用者下一輪的實測反應。

### 6. 側邊欄收合狀態持久化(`store/useStore.ts` + `components/Sidebar.tsx`)

**根因**:`Sidebar.tsx` 的收合狀態原本刻意用元件本地 `useState`,理由是「暫態的畫面偏好,
不值得擴大持久化範圍」——但對使用者來說,這不是無感的暫態,是每次開 App 都要重新收一次
的煩擾:「當 App 啟動後選單不知道為何會自動展開」。

**修法**:新增 `Settings.sidebarCollapsed`(persist v10→v11),`Sidebar.tsx` 改讀寫
`useStore` 而非本地 state。`migrateSettings` 的既有 `{...DEFAULT_SETTINGS, ...rest}`
展開邏輯自動補上新欄位的預設值(展開),沒有額外遷移邏輯需要寫。

## 📐 決策

- **`buildCalibrationPatch` 的幅度檢查保留,不因為現在「理論上用不到」就刪掉**——它是
  一個通用純函式,呼叫端多一個以外的地方使用它時不該預設已經先驗證過。這不是重複勞動,
  是系統邊界上的防線(參考本專案一貫的「靜默失敗才是真正該修的缺陷」立場)。
- **AUTO_STABLE_MS(1.5 秒的窗口時間)刻意不動,只調窗口內的樣本數門檻**——使用者原話
  「秒數也太少了」有兩種可能解讀(倒數太短/穩定窗口太短),但拉長穩定窗口只會讓免手擷取
  更難觸發,跟「有時不會自動開始」的另一個抱怨方向相反。倒數秒數(3→4)有明確文字不一致
  可以佐證,穩定窗口沒有,所以只動前者、放寬後者的樣本數門檻(不等於放寬時間長度)。
- **不做即時穩定度進度條**——「偵測中」的靜態文字提示已經是成本最低、風險最低的第一步,
  真正的 0~100% 進度需要額外的節流訂閱與 state,在這輪修復不確定使用者實際不滿意的
  具體點時,不值得先做到那個程度。

## ✅ 驗證

- `npm run ci`(typecheck + test + build)全綠,**290 tests**(286 → 287 新增 v11 遷移測試
  → 290 新增 3 個校準精靈假時鐘回歸測試)。
- **新增的假時鐘整合測試**(`CalibrationWizard.test.tsx`,原本此檔案的既有註解明確說明
  「涉及 capture() 真實倒數與取樣計時器,這裡不測」——這次改的正是這條路徑本身的行為,
  值得把假時鐘的複雜度換成真的回歸鎖):
  - 大腿只抬 10°(< 20°)時停在步驟 3/6 並顯示「大腿動作幅度不足」,**不會**先跑到步驟
    5/6 才被送回來。
  - 大腿抬 25°(≥ 20°)時正常進到步驟 4/6。
  - 小腿只勾 8°(< 20°)時停在步驟 4/6 並顯示「小腿動作幅度不足」。
  - 過程中踩到一個測試本身的坑:一開始用 `screen.findByText`(內部靠 `waitFor` 真實計時器
    輪詢)在假時鐘啟用時整個測試卡死超時——改成 `act()` flush 後直接用同步的
    `screen.getByText` 才正確運作。用一支獨立的除錯測試檔案逐步印出 DOM 內容,
    先在最小情境跑通再組回完整測試,不是憑猜測改。
- 手動追蹤程式路徑確認:`finish()` 裡 `buildCalibrationPatch` 的
  `thighDeltaTooSmall`/`shinDeltaTooSmall` 是目前程式碼裡唯一會把 `step` 送回 2 或 3
  的路徑;外展捕捉本身的「偵測到晃動」失敗只會停在原步驟(`finish()` 的 `if (!stats)
  return` 不改變 `step`)——確認使用者說的「步驟 5/6 校正後跳回前面步驟」只可能是這條
  路徑,不是別的成因,修法對症。
- ⚠ **這批修復尚未在真實硬體上實測**——使用者下一步會直接拿新 beta 版在真裝置上驗證
  免手擷取觸發率與倒數手感,這是本次修復刻意的驗收方式(見「決策」段落的第三點)。

## Self-review

展開側邊欄,會不會被 `setSettings` 的 Session-中凍結校準邏輯擋下,導致收合按鈕在跑步時
突然失效?」——追蹤 `setSettings` 的實作:凍結只套用在 `CALIBRATION_KEYS` 這個特定集合
(offset/invert/axisSwap 等會改變角度算式的欄位),`sidebarCollapsed` 不在其中,
`splitCalibrationPatch` 會把它歸進 `allowed`(不凍結)那一半,原封不動寫入——PASS,
Session 進行中收合側邊欄不受影響,也不會產生「Calibration frozen」的日誌雜訊。
