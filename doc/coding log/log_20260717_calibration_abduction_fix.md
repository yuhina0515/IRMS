# 2026-07-17 變更日誌 — 外展(向外側擺)校正判斷邏輯改造

> **相關文件**:[[HOME|導覽首頁]] · [[log_20260717_calibration_abduction_meeting|前置:多代理會議裁決]] ·
> [[log_20260705_direction_calibration|前置:方向校正功能]]

## 🎯 目的

實作 [[log_20260717_calibration_abduction_meeting]] 的會議裁決:校準精靈第 5 步(向外側擺,
判定內外翻方向)是全精靈中唯一需要單腳站立的步驟,天生比其他步驟晃動大,但原本的判斷邏輯
(大腿、小腿兩軸都要各自 ≥15° 才算數,任一軸不足就整步失敗要求重捕)是六步中最不寬容的,
兩者疊加導致該步驟特別難過關。

## 🔧 變更內容

1. **roll invert 逐軸解耦**(`calibration.ts` `buildCalibrationPatch`):
   - 移除 `rollDeltaTooSmall` 錯誤碼與整步失敗邏輯。改為大腿、小腿各自獨立判定:
     哪一軸的擺動幅度 `≥ CAPTURE_ROLL_DELTA_MIN`(15°,未變),就用該軸捕捉到的正負號
     更新該軸的 invert 設定;未達門檻的軸維持原設定,**不強制整步重捕**。
   - **明確不採用**會議中曾提出的「改用 `max()`,任一軸過關即整步過關」方案——那會讓幅度
     不足、數值接近雜訊底噪的那一軸,借另一軸過關「矇混」把自己不可信的正負號寫入設定。
2. **外展步驟專用 stdDev 門檻**:新增 `CAPTURE_STD_LIMIT_ABDUCTION = 4`(一般步驟仍是
   `CAPTURE_STD_LIMIT = 3`)。`CalibrationWizard.capture()` 改吃 `stdLimit` 參數,第 5 步呼叫
   `capture(CAPTURE_STD_LIMIT_ABDUCTION)`;`buildCalibrationPatch` 內原本對外展 capture 誤用
   全域 3° 門檻的（原本因 wizard 端已先擋而不可達的)防禦性檢查,同步修正為使用外展專用門檻,
   避免兩處門檻不一致造成明明 wizard 已放行、patch 端卻又打回的矛盾。
3. **新增「方向已驗證」持久化旗標**(`useStore.ts`,persist **version 3**):
   `Settings.thighRollVerified` / `shinRollVerified`,預設 `false`。只有在該軸這次捕捉幅度
   確實 ≥15° 而被拿去設定正負號時才標為 `true`;跳過外展、或該軸這次沒過門檻,都維持原有
   verified 狀態不變(**不會**因為單次沒過就把已驗證的狀態清掉)。
4. **UI 提示**:`DashboardView.tsx` 沿用既有 `.calib-chip` 樣式,新增「已校準但 roll 方向未
   完全驗證」的警示(點擊可直接重開精靈);`SettingsView.tsx` 校準面板加一行文字,具體列出
   哪一肢段(大腿/小腿)尚未驗證。取代原本「跳過即無感」的狀態——會議裁決明確反對把
   「跳過」降級成比「重試」更難按(那會把平衡最差、最常失敗的使用者推去做更多次單腳嘗
   試),改用「跳過/沒過門檻都照樣可以完成校準,但未驗證狀態會持續顯示」這條路線。

## 🧠 關鍵決策

- **不強制整步失敗重捕**:單軸沒過門檻不再擋整個精靈流程,直接以「該軸沿用原設定」放行。
  對比會議裁決前的行為(任一軸沒過就要求使用者重新完成整套 3 秒倒數 + 最多 3 秒持穩的單腳
  動作),大幅降低平衡受限使用者的重試負擔,同時因為逐軸解耦不共用門檻判定,不會有雜訊軸
  矇混過關的風險。
- **stdDev 只放寬第 5 步,且放寬幅度保守**(3°→4°,而非會議中重設計派原提的 5–6°):
  單腳站立雜訊底噪確實較高,但放太寬會讓「晃動」與「壓線幅度」的雜訊區間重疊,增加誤判
  方向的風險。
- **不做最佳窗口搜尋/擷取中即時回饋**:會議裁決認為對單人小專案工程量偏高,且即時回饋在
  單腳平衡當下疊加視覺任務,對平衡本已困難的使用者可能是負面影響。留待日後視情況評估。
- **verified 旗標不因「這次沒過」而回退為 false**:避免使用者已經驗證過一次方向、之後某次
  重跑精靈時單純手滑或站不穩,就把先前正確的驗證狀態抹掉,造成不必要的警示疲勞。
