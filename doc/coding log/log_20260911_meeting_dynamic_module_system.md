# 2026-09-11 會議記錄 — 是否啟動 App 端執行期動態模組系統

> **相關文件**:[[HOME|導覽首頁]] · [[OPTIMIZATION]] · [[log_20260907_meeting_tauri_v2_evaluation|前例:Tauri 遷移裁決會議]]

## 問題

`OPTIMIZATION.md` 記載的「App 端執行期動態模組系統」(讓功能模組不整包發版就能更新、
使用者自選啟用)在 2026-09-10 定案要動工前必須先開一次三方裁決會議(比照 09-07 Tauri
遷移裁決先例)。依賴閘門(Tauri Phase 4 auto-update)已於 09-10/09-11 大致到位並實際
跑過一次端對端驗證。這場會議要裁決:

1. 依賴閘門現在是否真的足夠成熟到可以啟動這個系統?還是該等 Tauri 遷移完全 cutover
   (Phase 5,目前卡在硬體驗證閘門)之後?
2. 若啟動,第一步該做什麼——技術可行性 spike、manifest/版本比對格式設計,還是直接拿
   「校正模組重練」當第一個模組?
3. 第一方/第三方 plugin marketplace 現在要不要拍板?
4. 整個系統相對於「直接把校正功能重練成傳統非模組化精靈」的機會成本值不值得?

## 與會者與立場

- **啟動派(pragmatist)**:主張現在就啟動,但第一步必須是技術可行性 spike,不是
  manifest 設計也不是直接做校正模組。核心論點:依賴閘門今天才第一次被真的用過
  (beta.2→beta.3,含一次真實發生又自行解除的 CDN 傳播延遲),這個新鮮的實作經驗是設計
  模組交付機制最值錢的素材;把模組系統(尤其是不碰硬體的純前端模組)綁在卡著硬體驗證的
  Phase 5 cutover 上,違反專案規則(c)。自評最弱點:選校正當第一個模組本身站不住腳——
  Phase 4 的整包 auto-update 已經讓校正邏輯能隨時整包更新,模組系統真正獨有的價值
  (跳過整包發版、自選啟用)對這個選擇並不明顯。
- **等待派(risk analyst)**:主張等 Phase 5 完全 cutover 再啟動。核心論點:依賴閘門是
  「被用過一次」不等於「被證明可信賴」——auto-updater 只有一次生產環境成功案例,還帶著
  一個沒被真正診斷、自己消失的 CDN 怪癖,且「無回退路徑」是風險登記裡已知未解的缺口;
  把校正邏輯(還沒被真機驗證過的 atan2 數學)當成第一個動態模組,會讓故障時同時要debug
  三個未知數(校正數學、模組載入器、還沒被硬體驗證過的 Tauri BLE stack)。自評最弱點:
  如果使用者「App 全模組化」的意圖是認真且近期的,現在把校正做成非模組化的擋案,以後
  還是要重做一次遷就模組契約,這是承認會發生、沒辦法排除的重工成本。
- **單人維護者機會成本派(solo-maintainer advocate)**:主張校正修正現在就用傳統
  非模組化方式出貨,整個模組系統擱置到真的出現第二、第三個模組需求為止,且第三方 plugin
  現在就明確排除、不留伏筆。核心論點:專案規則(b)「修缺陷不擴大議程」——場域回報的
  「分不清哪個感測器錯」是一個已經有數學解法(09-08 會議的 atan2 方案)的診斷問題,不需要
  遠端載入/簽章/manifest 就能修好;技術 spike 已經被延過一次(09-10),不該再滑到「現在
  真的做」;動態掛載+SHA-256+簽章驗證+分層啟用這套固定成本只有跨多個模組才攤得平,現在
  只有一個候選模組,ROI 打不平。自評最弱點:如果使用者的模組化意圖是真的且近期,現在的
  非模組化校正重寫以後要重做一次遷就模組契約,是承認且沒排除的重工成本。

## 交叉詰問關鍵發現

- **等待派 → 啟動派**:指出啟動派的 spike 前提(CSP/asset protocol 允許執行期
  fetch+動態 mount)不是真的跟硬體驗證絕緣——`TAURI_MIGRATION_PLAN.md` 風險登記裡列的
  「25Hz 持續負載可能逼 Rust→IPC→React 橋接層改變執行緒模型」若真的發生,可能連帶改動
  spike 今天驗證過的同一個 CSP/asset 設定面,今天的答案會過期、得重驗。同時指出
  「momentum 會流失、tacit knowledge 會遺忘」的急迫性論證,被這個專案自己的紀錄紀律打臉
  ——`log_20260911_tauri_updater_pipeline` 已經把整條踩坑過程寫得清清楚楚,保存知識這件事
  早就在低成本地發生,不需要靠「趕快動工」來保存。
- **單人維護者機會成本派 → 等待派**:指出等待派把一個純桌面、不碰硬體的決定(spike 該不該
  做)跟一個卡在硬體驗證的閘門(Phase 5)綁在一起,直接違反專案規則(c)——spike 本身
  100% 桌面軟體工作,零硬體依賴。也指出「等一個真實發生的 rollback 案例」是一個沒有排程
  終點的樂透,對一個低頻發版的單人專案而言,可能永遠等不到;正確做法是主動設計並測試
  rollback 路徑(可排程的任務),不是被動等一個壞版本自然出現。
- **啟動派 → 單人維護者機會成本派**:指出「等 #2/#3 具體出現再做」缺少任何觸發條件,而
  這個開發者的專案史(memory 記錄的「內部架構優化」——僅完成 code-splitting、範圍從未
  再確認、擱置至今)證明在他身上,沒有強制觸發點的「以後再說」實際結果就是永遠不做,
  搭配使用者一週只有週二晚上真正有空的行事曆更是如此。也指出一個內部矛盾:機會成本派
  一邊質疑 auto-updater 管線不夠成熟到能承載模組抓取,一邊又把「現在就該用同一條管線
  出貨校正修正」的急迫性建立在這條管線一定會順利運作的假設上——兩者不能同時成立。

三方交叉詰問後有一個明顯收斂:**沒有人在被攻擊後還堅持「校正模組重練」應該是動態模組系統
的第一個生產模組**——啟動派自己承認站不住腳、等待派主張這樣做疊加三重未知數風險、機會成本
派主張這違反修缺陷原則。這是本場會議裡三方立場交叉後唯一完全一致收斂的結論。

## 裁決

**拆成兩條互不依賴的軌道同時推進,不是「全做」也不是「全等」:**

1. **校正精靈重新設計 → 現在就做,走傳統非模組化路線**,採用 09-08 會議已經診斷過的
   raw-vector rotation + atan2 方案,不等模組系統就緒。
2. **動態模組系統 → 只做已經被延過一次的技術可行性 spike**,範圍嚴格限定為:一個不碰
   BLE/DB/OTA、跟校正邏輯無關的最小「hello world」模組(fetch 一段遠端純前端 JS →
   checksum+簽章驗證 → 執行期掛載),用來回答一個具體技術問題(Tauri 的 CSP/asset
   protocol 是否真的允許這個動作)。**明確排除**把校正模組當這個 spike 的實驗對象——
   兩件事的失敗模式必須分開驗證,不能疊在一起除錯。manifest 格式設計與正式模組交付機制
   (簽章金鑰管理、版本比對邏輯、Settings UI 呈現)全部暫緩,不在這次 spike 範圍內。
3. **第一方/第三方現在就拍板:只做第一方,不留第三方 plugin marketplace 的伏筆**——
   啟動派與機會成本派都主張現在拍板,等待派沒有異議。

**理由:**

1. 三方交叉詰問後唯一一致收斂的結論——校正不該是模組系統的第一個生產模組——直接決定了
   軌道 1 和軌道 2 必須拆開,而不是把校正塞進模組系統框架裡才動工。這解除了原本看似三選一
   的僵局:不是「啟動 vs. 等待 vs. 擱置」在打對台,而是這三個立場其實在爭論兩件不同的事,
   拆開後各自的最強論點都保得住。
2. spike 該不該現在做:機會成本派攻破等待派「等 Phase 5 cutover」的論證——一個不碰硬體的
   純桌面 spike 被卡在硬體閘門上,是專案自己的規則(c)明確要防止的反模式。且 Phase 5
   現在有實質進度(harold1008 正拿裝置跑 issue #3 的驗證腳本),不是遙遙無期,但也不該讓
   純軟體工作無條件等一個自己不掌控時程的外部進度。
3. spike 不該無限期擱置:啟動派攻破機會成本派「等 #2/#3 出現」的論證——這個專案自己的
   歷史紀錄(內部架構優化案)證明對這個特定開發者,沒有觸發條件的「以後再說」等於「永遠
   不做」。spike 本身成本低、範圍窄、可以在一次坐下的時間內做完,沒有理由連這個都無限期
   延後。
4. spike 不該擴大成「順便把 manifest 跟校正模組都做掉」:等待派攻破啟動派最積極的版本
   ——spike 的答案可能因為 Phase 0 硬體驗證發現的問題(25Hz 負載逼橋接層改架構)而過期,
   現在就把 manifest 格式和校正模組的建置流程押在今天的答案上,是雙重工的風險;「趕快做
   免得遺忘」的急迫性也被這個專案自己嚴謹的 coding log 紀律削弱——知識已經在低成本地被
   保存,不需要用趕工來保存它。

## 留意的異議(最強的反面意見)

啟動派攻破機會成本派的論證本身很有力,但反過來看也適用於 spike 自己:如果 spike 做完之後,
真的遲遲沒有出現第二個模組需求,這個 spike 本身也可能變成又一個「做了但沒有下文」的半成品
基礎建設——跟「內部架構優化」是同一種失敗模式,只是提早了一步發生。**監控方式**:spike
完成後,不論結果是「可行」還是「不可行」,都必須在 coding log 裡寫下明確的「繼續/停用」
判斷與下一步時間點,不能讓 spike 本身也變成一個新的、無限期懸置的「已經開始但沒有結論」
條目——這正是本場會議想避免、卻也最容易在執行時不小心重蹈的坑。
