### T(測試視角)

框架切錯縫。jsdom + @testing-library 抓不到 8/07 那個缺陷——那是**遺漏**不是迴歸,
而會想到寫那個測試案例的人早就直接把程式改對了。抓得到遺漏的工具是**寫下不變式**:
「任何歸零操作之後,被歸零的那個姿勢必須四軸都讀 0」。T 把它寫成測試、掃過全部 2⁶ 種
旗標組合,修好的 `buildQuickZeroPatch` 64/64 通過——**同一支測試在 `main` 上抓到第二個
未修的同類缺陷**(見下)。約 35 行,零新依賴。

### D(資料視角)

issue #4 錯了兩處。第一,它宣稱被「需要真實資料才能定案 schema」擋住,但快照形狀由
今天的 `Settings` 型別完全決定,不需要資料。第二,**四個 raw 欄位是多餘的**:
`applyCalibration` 是通道置換 + 仿射映射,置換只交換兩個**都已儲存**的通道,
`normalizeDeg(±x + c)` 在 mod 360 下是雙射,EMA 對 `shortestArcDelta` 是線性因此可交換。
D 寫探針實跑 300 筆(刻意讓兩個通道跨 ±180 分支切點),在三種錯誤設定下重建誤差
< 1e-6°,對照組確認測試會失敗。成本面:raw 欄位 +36 bytes/列,25Hz 十分鐘 session
= 15,000 列 → **+540 KB/場、+54 MB/百場**,而快照 JSON 只要約 200 bytes。

## 🐛 會議期間發現的新缺陷(三方獨立收斂,已出貨)

**根因:offset 是「帶符號摺疊」儲存的,而 invert 開關不重算 offset。**

- 寫入端(`calibration.ts:171`、`buildQuickZeroPatch`):`offset = -(eff.axis × (invert ? -1 : 1))`
- 讀取端(`useStore.ts:296`):`value = normalizeDeg(raw × sign + offset)`

兩者相乘後在校準姿勢下得 0,正確。但使用者在「進階手動校準」按下「Invert Thigh 反相」
(`SettingsView.tsx:113`)時,`sign` 變號、`offset` 原封不動,於是校準姿勢下的讀值變成:

```
raw × (−sign) + (−raw_calib × sign)  =  −2 × sign × raw_calib
```

raw = 30° 時正好是 **−60°**。不是方向翻轉,是方向翻轉**外加兩倍偏差**。
一次點擊、沒有任何錯誤訊息、已隨 **v1.0.1 出貨**。

**這與 2026-08-07 的缺陷是同一個類別**:同一組耦合欄位有多個寫入者,但只有一部分寫入者
維護那個不變式。八週內同一個檔案發生第二次。

D 在交叉詰問中獨立以執行驗證重現到小數九位,並指出**修正後的正確 offset 恰好是原值的負數**
——這正是符號摺疊的直接後果。

## ⚔ 交叉詰問

### 對 D:raw 欄位真的多餘嗎?不連貫的設定組合怎麼辦?

主席把 T 的 raw 欄位主張與「快照記的是 App 相信什麼、不是當場量到什麼」(O)一併轉給 D。

**D 讓一半、駁一半:**

- **駁**:可逆性證明在不連貫的設定下**依然成立**。`x·s + o` 對任意 `(s, o)` 都可逆,
  與這組值在物理上有沒有意義無關。D 特地重跑:以不連貫的 `(invert: true, offset: −30)`
  錄 400 筆跨切點樣本,儲存的紀錄比真值差 **> 30°**,而純快照重建把四個基礎通道連同
  衍生的 `knee`/`kneeRoll` 全部還原到 **< 1e-6°**。raw 欄位在此情境同樣沒有貢獻。
- **讓**:**快照無法宣告自己不連貫**,這是設計的真實缺口。`{thighInvert: true,
  thighOffset: −30}` 單看每欄都合法、合起來是胡說,而「符號摺疊」是沒有文件的內部慣例,
  三個月後的督導無從判斷。
- **補救(且免費)**:把校準姿勢本身存下來(`calibrationPose`,persist v4——精靈在
  `apply()` 時本來就握有 `capturesRef.current.baseline.mean`)。見證值就是
  `applyCalibration(calibrationPose, settings)`,**當且僅當設定連貫時四軸為 0**。
  實測:連貫 → < 1e-9;翻轉 invert 後 → 60。快照因此能自己宣告缺陷。
- **對 O 的欄位讓步**:O 的區分正確且 D 的設計蓋不到——見證值回答的是「設定與它被推導出來的
  那個姿勢是否自洽」,回答不了「感測器是不是還在校準當時的位置」。護具重綁高兩吋會產生
  一個完美為 0 的見證值和一份系統性錯誤的紀錄。**只有 session 開始時的新鮮量測能區分兩者。**
- **對主席二選一命題的反駁**:那是假兩難,因為它預設了離散型別欄位。migration 6 應該只加
  **一個** `sessions.calibration TEXT` 存版本化 JSON(十個校準欄位 + `lastCalibratedAt`
  + `calibrationPose` + `witness` + `zeroCheck: null`)。日後補 `zeroCheck` **完全不需要
  migration**。理由也站得住:不像 `safetyLimit`/`triggerType` 會被圖表當純量個別讀取
  (`HistoryView.tsx:38-50`),這十三個欄位從不被個別查詢,只會整組顯示與整組消費。

### 對 O:你的 UI 會不會替這個缺陷發合格證?

**O 完整讓步,而且指出情況比主席說的更糟一階。**

O 先自行複核(20 萬組隨機案例含跨切點):確認兩倍偏差,並找出精確簽名——
**校準姿勢下的殘差恆等於 `2 × offset`**,20 萬組全中、誤差 0。

然後 O 補上主席沒點出來的那一層:**今天這個缺陷是「吵」的,而 O 原本的 UI 會把它變「安靜」。**
在 `segment_elevation` 下,誤按 invert 之後患者站直、量表大字直接寫 **−60**——荒謬到會被看見。
走一遍原提案:檢查零位 → 殘差 −60 → 不通過 → 重新歸零 → 站直讀 0 → 綠勾。
**站直讀 0 遠比 −60 可信,而方向是反的。**

最壞的是 `segment_extension`(`value = -angles.thigh`):thigh 反相後,患者把腿**往前**抬,
App 記成後伸量增加 → 進目標帶 → `onRepCompleted` → 下發 `CMD:GOAL` 蜂鳴器響 →
`repsCompleted` 寫進 DB。**一場方向完全做錯的療程被完整記錄成達標。**
O 據此撤回原本「措辭誠實」的緩解:這個失效模式應該被**結構消滅**,而不是被文案警告。

**O 提出的結構修正(本次會議的核心產出)**:offset 改為不折符號地儲存——存校準姿勢當下的
raw 讀值 `zeroRaw`,判定改為 `(raw − zeroRaw) × sign`。

- 與現行程式**數學等價**,全圓最大差 **5.7e-14**(浮點噪音,非行為變更)
- Settings 遷移公式 `zeroRaw = -offset × (invert ? -1 : 1)` 無損,走既有 `migrateSettings`
- `buildCalibrationPatch` 步驟 4 與 `buildQuickZeroPatch` 都**變短**(設計變簡單是好訊號)
- invert 從「誤觸即雙倍偏差的地雷」變成語意清楚、可逆、不擾動零位的合法控制項

### O 對「先補測試」的一半讓步 —— 以及一個關鍵論點

O 接受「UI 不該排在測試前面」,但爭 (A) 的**內容**。把兩個已證實的缺陷各問一次
「什麼測試會抓到它」:8/07 那個是 `calibration.ts` 的純函式測試(不需 jsdom);
這次的 invert 是 `setSettings` 後對 `applyCalibration` 斷言(store 層,React 不在路徑上)。
**兩個真實缺陷沒有一個需要元件測試。**(A) 的前提「bug 活在沒測試碰過的 React 元件裡」
描述的是程式碼**當時坐在哪裡**,而兩次的正解都是把它**搬出來**,不是原地測它。

而 O 最關鍵的一句(也是它讓步的理由):**這一類缺陷測不到,是因為 schema 沒有留住
不變式所指的那個事實。**「站直必須讀 0」今天寫不成斷言——offset 折過符號,App 校準完
就不再知道「站直」是什麼。存了 `zeroRaw` 之後,不變式變成一行且**由建構保證**:

```
∀ settings: applyCalibration(zeroPose(settings), settings).thigh === 0
```

**所以結構修正不是排在測試前面,它是讓那個測試第一次寫得出來的前提。**

## 🔬 主席補充覆核(T 中斷後由主席自行完成)

T 被交付的四個問題(可逆性能否撐過真實讀取路徑)因額度中斷未答完,主席自行讀程式碼判定:

| 疑點 | 判定 |
|---|---|
| LTTB 抽樣 | **不影響**。只在讀取時作用,且 `db.ts:157` 的 `.map((p) => p.r)` 回傳**原始列本身**而非內插點;CSV 匯出不傳 `maxPoints`,取全量 |
| 封包遺失 | **不影響**。EMA 走實際收到的封包序列,重建是逐點仿射,兩邊看到同一串樣本 |
| EMA 初始狀態 | **可還原**。`seeded` 讓第一筆直接落地(`y₀ = x₀`),無不可還原暫態;`reset()` 只是重新播種 |
| NaN / 畸形封包 | **不影響**。`protocol.ts:125` 在進入管線前丟棄,不會進資料庫 |

並補上 D 未明寫的關鍵一步:EMA 對 `a = ±1` 的仿射映射可交換,因為
`shortestArcDelta(g(u), g(v)) = a·Δ(u, v)`,故 `g(yₙ) = g(yₙ₋₁) + α·Δ(g(yₙ₋₁), g(xₙ))`。
**D 的可逆性證明成立,raw 欄位確實多餘。**

### T 補答(重試後完成,四題結論與主席獨立判定一致)

T 以收窄後的問題重跑並**完整撤回 raw 欄位主張**,其控制組重現單一設定下的重建精度為
基礎通道 1.7e-13°、衍生 `knee` 2.3e-13°(對照組確認未修正資料 > 10° 錯)。
四題全數「不構成破壞」,理由與上表一致。T 另帶回**兩個主席與 D 都沒抓到的發現**:

**(甲)LTTB 的選點鍵是未修正的膝角。** `db.ts:156` 的抽樣鍵為 `y: r.kneeAngle ?? 0`,
而 `downsample.ts` 的明示目的是保峰(「均勻取樣會直接錯過落在取樣點之間的峰」)。
於是**事後做修正性重建時,被保留下來的是「錯誤曲線」的峰,真正修正後的最大值可能坐在
被丟棄的那一列裡**。T 同時指出這不救 raw 欄位——raw 欄位坐在同一批被丟棄的列上,一樣沒了。
**正解是:任何修正性重新分析都要走全量讀取(不傳 `maxPoints`,CSV 匯出路徑已經是這樣)**,
而不是加欄位。

**(乙)真正會打破快照重建的是「session 進行中重新校準」,而它今天完全沒被擋。**
`bluetooth.ts:167` 每收一個封包就即時讀 `this.store.settings`;而 `setView` 無守衛
(`BottomBar.tsx:39`)、快速歸零**完全沒有 `disabled`**(`SettingsView.tsx:125`)、
精靈的 `disabled={!isConnected}` 在錄製中恰恰為 **true**(即可用)。單一 session 快照是
單一 `(s, o)` 組合,**描述不了一條兩段制的資料流**。T 實測:操作者在第 300 筆的第 150 筆
按下快速歸零 → 純快照重建在最差通道錯 **57.00°**、`knee` 錯 **45.00°**;raw 欄位重算則為 0。

**T 拒絕用這一點來救 raw 欄位**,理由是讓這個情境**不可表達**遠比為它買 36 bytes/列便宜:
在 `session.running` 時鎖住校準控制項。那個守衛本來就該做——錄製中重新校準無論存什麼都會
汙染紀錄。**「出守衛,不是出欄位。」**

T 誠實保留的唯一 raw-only 能力:重建無法在**不同濾波參數**下重跑。若日後把
`EMA_ALPHA` 從 0.3 調到 0.5,純快照重建與新 α 的真值差 **8.38°**,raw 欄位則精確。
T 自評這是「未來能力」論證而非正確性論證,不值 54 MB/百場。

## 🏛 主席裁決

**框架被三方共同推翻。** 沒有任何一位參與者的初始提案獲勝——交叉詰問後三方收斂到
一個沒人一開始提出的東西:**帶符號摺疊的 offset 表示法才是根因,重新參數化它是其餘
一切的前提。** 裁定順序:

1. **結構修正:offset 改存 `zeroRaw`,判定改為 `(raw − zeroRaw) × sign`** + 由建構保證的
   不變式測試。**0.5–0.75 人天,純 vitest,零真機需求。**
   - 這是**修掉已出貨 v1.0.1 缺陷的正解**,而且是用結構消滅、不是用偵測補救。

## ⚠ 最強的存活異議(需持續監看)

**結構修正不解決方向錯誤。** 使用者誤按 invert 之後,站直仍讀 0(正確),但抬腿方向是反的,
而零位檢查會說「零位正常」——那句話為真,但操作者要的答案不在那句話裡。
要驗方向就需要 ≥20° 的動作,也就是 O 最初拿來攻擊精靈的那道門檻——**低 ROM 患者做不到,
而這個洞在修完之後原封不動。**

`residual ≡ 2×offset` 那個簽名只在「offset 算完之後才翻 invert」這條特定路徑上成立,
翻完再重新歸零就查不到。誠實的結論:**這一批把「安靜的錯」少掉一類,沒有變成零。**

**次要監看項一:修正性重新分析必須走全量讀取。** T 發現 LTTB 的選點鍵是未修正的
`kneeAngle`,保峰保的是錯誤曲線的峰。日後若真的要用快照重建歷史 session,
**必須不傳 `maxPoints`**,否則真正的修正後峰值可能已在抽樣階段被丟棄。
此限制應寫進重建工具的註解裡,否則它會安靜地生效。

**次要監看項二:重建無法換濾波參數。** 若日後調整 `EMA_ALPHA`(0.3 → 0.5 實測差 8.38°),
既有 session 無法在新參數下重跑。這是接受 raw 欄位被砍的已知代價。

次要監看項三:migration 6 採 JSON blob 而非離散欄位,代價是這十三個欄位無法被 SQL 個別查詢。
現況下它們只被整組顯示與整組消費(不像 `safetyLimit`/`triggerType` 會被圖表當純量讀),
但若日後需要「找出所有 `thighAxisSwap = true` 的 session」這類查詢,就得改用
`json_extract` 或再開一次 migration。
