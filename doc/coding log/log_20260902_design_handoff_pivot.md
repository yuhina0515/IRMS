# 2026-09-02 變更日誌 — 轉向外部設計支援,建立 Gemini handoff 套件

> **相關文件**:[[HOME|導覽首頁]] · `doc/gemini-handoff-20260902/README.md` ·
> `doc/gemini-handoff-20260820/README.md`(上一次同類型 handoff,本次沿用同一套慣例)

## 🎯 請求

使用者在 Phase 4 完成 Settings 重建 + 兩輪尺寸微調後,回饋:「我們需要外部藝術支援,太醜了,
不管是 UI 設計還是色彩。」並先嘗試 `/plan`(此環境不支援該指令)——這個嘗試本身是個訊號:
使用者要的是停下來想清楚方向,不是繼續要求下一顆按鈕再調小一點。

## 🔍 根因確認

先誠實檢討:先前幾批的「錨定真實來源」只做到了一半——色票(`tailwind.config.js` 的
`canvas`/`surface`/`accent`...)確實是 Tailwind 官方調色盤的真實 hex 值,不是憑印象發明;
但**排版節奏、間距韻律、視覺層次這些真正決定「耐不耐看」的東西,從頭到尾都是我自己的判斷
組出來的,沒有一次對照過真正做得好的深色 dashboard/bento 實例**。單顆色票數值正確
(WCAG 過關)不等於組合出來的整體畫面耐看——這正是使用者說「色彩也醜」的根本原因,不是
色票選錯,是組合方式沒有經過真正設計過的東西驗證。

## 🔧 已完成

用 `AskUserQuestion` 給三個實質不同的「外部藝術支援」選項:

1. 拉真實元件庫成品來拼(Aceternity/Magic UI 等)
2. 對照真實產品截圖(Linear/Vercel/Grafana)逐項比對差距
3. 改用專門的 AI 設計/畫圖工具出 mockup,我對照忠實實作

**使用者選第 3 項**——角色從「設計+實作」改成只做「實作」,設計判斷交給外部工具。

查證發現本專案 **2026-08-20 已經做過同一類型的 handoff**(`doc/gemini-handoff-20260820/`:
螢幕截圖 + README 說明畫面內容/色彩系統/字體,交給使用者帶去 Gemini 3.1 Pro 網頁版手動操作,
不接 API)。沿用同一套慣例,建立 `doc/gemini-handoff-20260902/`:

- 隔離 `--user-data-dir` 啟動封裝產物,暫裝拋棄式 `playwright-core` 連 CDP 截取現況四張
  螢幕截圖(Dashboard/Actions/History/Settings)。
- 新 README.md 比照舊版結構,但內容更新為:①**明確劃出已定調、不該被重新辯論的範圍**
  (不再是 Apple/Liquid Glass、固定深色主題、bento 方向、單頁殼)②**明確劃出真正待外部
  設計判斷的範圍**(排版節奏/視覺層次/色彩組合整體觀感,以及 Settings 這個唯一已經動過
  設計的畫面其實仍是被嫌醜的那個,不該被當成標準抄)③ 列出目前色彩/字體/圓角 token 的
  真實數值(給需要推理精確 token 的工具用)④ 誠實標註 Dashboard/Actions 兩頁尚未真正重建
  (仍是繼承通用卡片樣式,不是設計後的結果),避免外部工具誤判成「這是設計過的成品要改進」
  而不是「這是還沒設計過的半成品」。

## 🧠 關鍵決策

**README 明確劃出「已定調不可逆」與「待設計判斷」兩個範圍,不是把整個方向丟給外部工具重新
決定**:如果讓外部工具連 IA/主題策略都重新提案,很可能得到一份跟現有 `ROADMAP.md` D5、
`UI_REDESIGN.md` 衝突的方案,徒增協調成本。已經是使用者親自裁定過的決策(單頁殼、固定深色、
不走 Apple 語系)應該被當作邊界條件交代清楚,外部工具的價值該放在「這些邊界條件裡面,
排版節奏跟色彩組合怎麼做才好看」這個真正還沒解決的問題上。

**誠實標記 Dashboard/Actions 尚未重建**:如果不說明,外部工具可能會把「還沒認真做的東西」
當成「已經盡力設計但失敗的東西」來分析,診斷方向會偏掉。

## ✅ 驗證

純文件與截圖產出,無程式碼變更,不適用 `npm run ci`。驗收腳本、暫裝的 `playwright-core`
用完即刪,`git status` 只剩四張截圖與一份 README。

## 🔎 自我審查

**檢查情境:這份 handoff README 會不會不小心把「已經定案」的東西寫得語氣像是仍可商量,
或反過來把「其實還有彈性」的東西寫死?**——逐段重讀:IA/主題/bento 方向三項明確標注
"don't re-litigate"「不是設計選項」;唯一寫進「已定調」區塊但同時保留彈性的是 History
不套 bento 的判斷,原文特別註明「這個具體決定可以被更好的想法推翻,但背後的判斷邏輯
(bento 適不適合這個內容形狀)該延續」——避免外部工具把它誤讀成鐵律或誤讀成完全開放。
**Pass**。
