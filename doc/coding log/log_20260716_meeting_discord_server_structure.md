# 2026-07-16 會議紀錄 — IRMS Discord 伺服器結構決策

> **相關文件**:[[HOME|導覽首頁]]
> **主題**:IRMS 專案 Discord 伺服器的身分組、分類/頻道、IRMS-Bot 權限該如何設計?
> **參與者**:精簡實用派、風險治理派、組員使用者派
> **椅子決定**:3 層身分組、頻道維持現狀不做領域細分、bug 回報導向 GitHub Issues、IRMS-Bot 立即踢除重邀

---

## 議題框架

**決策**:IRMS Discord 伺服器(guild `1527032318823235715`)的完整結構該是什麼?具體包含身分組設計、分類/頻道配置、IRMS-Bot 目前 Administrator 權限的處置。

**背景**:
- 專案:IRMS(智慧復健監測系統)——ESP32 穿戴感測 + Electron 桌面 App,已發布 v1.0.1,71+ tests 全綠。
- 團隊規模:個位數到十幾人,純內部專案協作,非公開社群。
- 涉及三個技術面向:硬體(ESP32/感測器)、韌體(embedded C/C++)、App(Electron+React+TS)。
- 伺服器現況:分類「專案討論」(#一般、#開發討論、#bug回報)、「公告與資訊」(#公告)、「語音頻道」(一般);完全沒有自訂身分組,只有 @everyone。
- **事故背景**:瀏覽器自動化操作 OAuth 邀請流程時,因點擊時序問題,IRMS-Bot 在使用者尚未最終確認前就已自動取得 Administrator(完全控制)權限。同意畫面上出現一行不明權限描述「烤個蛋糕」,不符合任何標準 Discord 權限字串,原因未查明。此外,IRMS-Bot 與另一個既有專案(Minecraft 伺服器)的 Hina-Bot,兩組 Bot Token 都曾被明碼貼進聊天紀錄。

---

## 三方立場總結

### 1️⃣ **精簡實用派** — 主張最小結構

**立場**:2 個身分組(@everyone + Admin),頻道完全不變,IRMS-Bot 立即降到無權限。

**前 3 大理由**:
1. 每多一個身分組/頻道都是永久的維護成本與新人解說成本,十幾人的團隊不需要徽章系統。
2. 專案自身 git 紀錄顯示硬體/韌體/App 工作**不是**乾淨分離的(同一週的 commit 常常三者都碰),領域分權限只會傷到最常跨領域的人。
3. 目前沒有任何功能需要 Administrator,收回是一鍵動作,沒有「先留著比較快」的論點;「烤個蛋糕」這種無法解釋的權限字串應視為硬性停止訊號。

**自承最弱點**:扁平結構沒有「何時該升級」的觸發機制(團隊擴編、外部協作者、機密文化),之後要在已運作的扁平結構上補身分組會比現在直接做更痛。

### 2️⃣ **風險治理派** — 主張分層身分組 + 徹底的 Bot 重置流程

**立場**:4 層身分組(Owner/Core Dev/Member/@everyone),IRMS-Bot 踢除、重新產生 token、查明異常字串後才重邀且僅給列舉出的最小權限,通知改用 webhook 而非 Bot 登入身分。

**前 3 大理由**:
1. Administrator + 已在明碼聊天中外洩的 token,是同一個風險被放大,不是兩個獨立風險——之後有人翻聊天記錄找到還活著的 token,對 Administrator 級 Bot 跑腳本可以在幾秒內清空整個伺服器。
2. 小團隊不會回頭檢視「已經在運作」的權限,現在改幾乎零成本,一年後累積更多依賴再改是一個專案量級的工程。
3. 「烤個蛋糕」這種異常字串正是最容易被理性化忽略、卻最不該被忽略的訊號——安全意識強的團隊面對「這個授權畫面出現看不懂的東西」的反應不會是「先授權,之後再查」。

**自承最弱點**:整套建議假設團隊真的會去 Developer Portal 查證實際權限整數,而非「勾少一點就重邀」——但這個團隊已經證明過會讓自動化腳本無人監督地點過同意畫面,同一種捷徑心態可能重演。

### 3️⃣ **組員使用者派** — 主張依技術領域細分頻道 + 標籤身分組

**立場**:Owner/Core/Member + 自選標籤身分組(@硬體/@韌體/@App),頻道依領域拆成 🔧硬體/💾韌體/💻App 三個分類,#bug回報 改成帶標籤的論壇頻道,另加新人指南頻道與一個配對用語音頻道。

**前 3 大理由(附專案實據)**:
1. 引用 `log_20260704_firmware_v3_rewrite`(韌體重寫)與 `log_20260711_trigger_stability`(App 端遲滯/EMA 調參)兩則日誌,證明「開發討論」對硬體/韌體/App 三種讀者的相關度天差地遠,混在一個頻道會互相淹沒。
2. 引用 `log_20260714_bottombar_layout` 記載的真實 React StrictMode 缺陷,主張 bug 需要可追蹤、可搜尋的結構,而非埋進聊天紀錄。
3. Administrator 權限一旦出事,承受後果的是每天倚賴頻道歷史記錄的一般組員(例如當初討論過的 IMU 接腳細節),不是核准權限的管理者本人。

**自承最弱點**:專案自己的架構文件(D1 決策)寫明韌體被刻意精簡、判斷邏輯全部收斂在 App,韌體與 App 在 BLE 協定邊界高度耦合——三分頻道可能製造它想解決的同一種碎片化問題(跨頻道貼、不知道該貼哪裡),而單一 #開發討論 搭配 Discord 討論串或許能用更低的切換成本達到同樣效果。此點信心不足。

## 交叉盤問結果

### 風險治理派 → 攻擊精簡實用派的扁平結構

三個具體漏洞,超出精簡派自承的弱點:
1. **扁平結構對「這個團隊已經發生過兩次」的事(明碼貼 token)沒有快速反應能力**——只有 1-2 位 Admin 有刪訊息權限,若半夜有人為了解 build 卡住貼了憑證,兩位 Admin 都不在線,外洩訊息會留在所有人都看得到的頻道裡數小時甚至數天。
2. **扁平權限沒有任何「縮小曝光範圍」的中間層**——訊息一貼出就是全體成員可見,沒有結構能表達「這個頻道/討論串預設少一雙眼睛看」。
3. **「重邀要人工審查」只是說法,不是被結構強制的規則**——若重新設定 Bot 權限的帳號跟原本誤點授權的帳號是同一批 1-2 位 Admin,沒有任何機制要求雙人覆核,這正是導致本次事故的同一種失效模式(一人一鍵無審查)。

風險治理派同時承認:精簡派「不用照領域細分頻道/身分組」這個論點站得住腳,git 紀錄證據充分,無法反駁。

### 組員使用者派 → 攻擊風險治理派的分層/webhook 方案

同意 token 輪替、踢除重邀、MFA-only Owner 帳號等後台動作完全正確、對組員日常體驗零影響,無異議。但指出兩個實際缺口:
1. **「保留現有 4 個頻道」原封不動,加一個 #bot-log 收 webhook 通知,沒解決「通知該依相關性分流」的問題**——如果韌體 CI 和 App CI 的建置通知混在同一個頻道,韌體的人一樣要滑過所有 App 的通知(反之亦然),webhook 解決的是「怎麼發」不是「發去哪」。
2. **「絕不貼即時憑證,沒有例外」對這個專案有真實缺口**——`IRMS_Sensor/config.h` 的 WiFi SSID/密碼是硬體 bring-up 時的正常、反覆需求,完全禁止且沒有指定安全管道,只會把分享行為推去沒人看得到、無法稽核、沒有輪替紀律的 1:1 私訊,反而更難掌握。

### 精簡實用派 → 攻擊組員使用者派的領域細分方案

三個具體反駁:
1. **結構數量超過團隊人數**:完整方案是 8 個文字頻道 + 2 個語音頻道 + 6 個身分組,對「個位數到十幾人」的團隊而言,人數下限時結構比人還多;第一週就會出現好幾個頻道零訊息、顯眼地「看起來被棄置」。
2. **自選標籤身分組會悄悄過期而沒人發現**——依照這個專案自己的 commit 紀錄,同一個人常常同一週內橫跨韌體與 App,標籤沒有人負責維護,半年後新人 tag 錯人的機率很高。
3. **#bug回報 論壇頻道跟專案既有的 GitHub Issues 形成兩套紀錄系統**——這是一個有 71+ tests、有 GitHub Release 發布流程的 repo,bug 幾乎必然該連到 commit/PR,而不是 Discord 裡一個平行的、容易被日常聊天習慣繞過的追蹤系統。

精簡派表示除了對方自承的 D1 耦合弱點外,找不到更強的反對意見——這點才是真正站得住腳的核心問題。

## 🎯 椅子決定

### **裁決依「論點是否撐過交叉盤問」評分,而非發言自信程度**

**全員一致、且完全撐過交叉盤問的結論(最高信心):**
- IRMS-Bot 的 Administrator 權限必須立即處理——三方獨立提出、無人反駁。
- 「烤個蛋糕」異常字串必須查明(比對 Developer Portal 實際權限整數)才能信任該應用程式。
- Bug 追蹤應導向既有的 GitHub Issues,不建 Discord 論壇——精簡派論點未被反駁,使用者派自己也承認缺乏更強反例。
- 硬體/韌體/App **不**做領域頻道與身分組細分——使用者派自承的 D1 耦合弱點,被精簡派的三個具體反例(結構數量超編、標籤過期、bug 追蹤重複)獨立證實,不是各說各話,是同一個判斷被兩個角度分別驗證。

**身分組:採風險治理派的分層邏輯,但用精簡派的規模節制(3 層,非 4 層,也非 2 層)**
扁平 2 層在交叉盤問中確實露出真實漏洞(無快速反應、無曝光縮小、無審核強制),且這個團隊有「明碼貼 token 兩次」的實際前科,不是假設性風險。但 4 層裡的 Owner/Core Dev 已經涵蓋所有必要區分,不需要再疊加使用者派的標籤身分組(該提案已被推翻)。

| 身分組 | 權限 | 說明 |
|---|---|---|
| **Owner** | Manage Server/Roles/Channels、踢/禁言、唯一能動 Bot 權限設定的人 | 1-2 位真人,MFA 必開 |
| **Core** | Manage Messages/Threads/Pins,無伺服器結構權限 | 給活躍貢獻者,能立即刪除誤貼的憑證,不用等 Owner 上線 |
| **Member**(預設) | 除 #公告 外皆可發言 | 一般組員 |
| **@everyone** | 同 Member,但 #公告 唯讀 | 不另設訪客/試用層,精簡派原則保留 |

**頻道:維持現有結構,不擴張**
```
專案討論
  ├ #一般
  ├ #開發討論   (不拆分領域,原因見上)
  └ #bug回報    (輕量討論/篩選用,正式紀錄一律進 GitHub Issues)
公告與資訊
  └ #公告        (僅 Core 以上可發言)
語音頻道
  └ 一般         (暫不加專用配對語音頻道,待實際跨領域協作頻率證實需求再加)
```

**IRMS-Bot:完整重置流程(全員一致)**
1. 立即踢除 IRMS-Bot——未經審查完成的授權不算數,不是「先降級再說」。
2. 在 Developer Portal 重新產生 Bot Token(已在明碼聊天外洩,無論是否重邀都視為已燒毀)。
3. 重邀前,對照 Developer Portal 的 OAuth2 URL Generator 實際權限整數,查明「烤個蛋糕」對應到什麼——查不出來之前不重邀。
4. 重邀時僅給列舉出的最小權限,依 Bot 實際功能決定,不再給 Administrator。
5. 若未來需要 Bot 發通知(如 CI/build 狀態),優先用 Discord **webhook**(單頻道、只能發文、無法讀歷史/管理、可獨立輪替),而非用 Bot 本身的登入權限。
6. 同時輪替 Hina-Bot(Minecraft 專案)的 token——同一操作者、同一種外洩模式,不能只修 IRMS 這邊。

**機密分享規範(精修版,非全面禁止)**
- 正式/生產環境憑證:任何頻道、任何私訊都不得明碼貼出,無例外。
- **明確排除**:此專案有真實且反覆的需求要分享非生產測試值(例如 `IRMS_Sensor/config.h` 裡 ESP32 bring-up 用的實驗室 WiFi SSID/密碼)——這類值可以在 #開發討論 分享,但**必須明確標註為「測試/實驗室用」,不得是生產憑證**。全面禁止只會把真實分享需求推去無稽核、無輪替紀律的私訊,對想防的風險反而更糟。

**明確否決(附理由)**
- 硬體/韌體/App 領域頻道與標籤身分組——結構數量超過團隊人數下限、標籤會悄悄過期、跟專案自身的 D1 架構耦合證據矛盾。
- Discord 論壇型 #bug回報——與既有 GitHub Issues 形成重複的紀錄系統,不受歡迎的重複容易被日常聊天習慣繞過。
- 專用配對語音頻道——非現在就否決,是延後:等實際跨領域協作頻率證實需要,再加,不要為假設性場景先建。

## 決策根據

1. **論點品質而非語氣自信**:精簡派攻擊使用者派的三點(結構超編、標籤過期、bug 追蹤重複),與使用者派自己承認的 D1 耦合弱點方向一致、互相獨立印證,判定為高信心結論。
2. **實際事故記錄優先於假設性風險**:風險治理派對扁平身分組的攻擊之所以成立,是因為「明碼貼 token」在這個團隊已經發生兩次,不是推測——這把 Core 層的存在從「錦上添花」變成「已驗證需要」。
3. **不對還沒存在的功能先建結構**:Bot 通知路由分流(使用者派對風險治理派的批評)有道理,但 IRMS-Bot 目前沒有任何通知功能,依精簡派原則,等功能真的做出來時再依子系統分流,不用現在預建。
4. **專案既有基礎設施優先於平行系統**:GitHub Issues 已經是這個 repo 的事實標準,不重複造一套 Discord 論壇。

---

## 決議

**方案**:3 層身分組(Owner/Core/Member+@everyone)、頻道結構維持現狀不做領域細分、bug 走 GitHub Issues、IRMS-Bot 立即踢除並走「重置 token → 查明異常字串 → 最小權限重邀 → 未來通知優先用 webhook」完整流程、機密規範保留測試用值的例外通道。

**監控指標**:
- IRMS-Bot 重邀後的權限清單是否真的是「列舉最小集合」,而非「勾少一點但沒對照 Developer Portal」。
- #開發討論 是否在未來出現大到需要拆分的訊息量(而非現在預測性拆分)。
- Bot 未來若真的接上通知功能,是否在那時依子系統分流,而不是放著混雜下去。
